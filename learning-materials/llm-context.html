大模型的上下文 (LLM Context)

一句话定位：上下文是模型在一次推理中"看得见"的全部输入——prompt、对话历史、工具结果、检索片段，决定它这一次回答能走多远。

1. 学习目标 & 关键问题

读完能做：

  1. 用一句话讲清"上下文"对 LLM 意味着什么。
  2. 区分"上下文窗口"与"有效上下文"两个概念。
  3. 解释为什么跑长任务的 Agent 必须做"上下文管理"。
  4. 列出至少三种上下文管理的工程手段。
  5. 说出"上下文污染"在长任务中的常见表现。

  • "100k 上下文窗口"等于"能稳定利用 100k 的事实"吗？
  • RAG（检索增强生成）和"长上下文"是什么关系？是不是互斥？
  • Agent 跑久了为什么会"迷失"甚至开始自己瞎写？

2. 个人解释

用一个我自己的比喻：

LLM 的上下文 = 它开这一次会时桌上摊开的全部文件。模型每次推理只能看桌上有的，看不到的不存在。

对应三层概念：

  • 上下文窗口 = 桌子的大小（最多能摊下多少页）。
  • Token = 文件的字数/字符片，是模型的最基本计量单位。
  • 有效上下文 = 模型在这么大一张桌子上真的还能稳定看清楚的区域。这个区域往往比窗口小很多，而且在长任务中会越来越小。

所以"百万上下文"听起来很厉害，但能不能"稳定记住"百万字级别的事，是另一回事。Anthropic 在《Effective context engineering for AI agents》里也提示：上下文"多"不等于"有用"，要做主动管理[1]。

很多新手以为上下文 = 模型"记住了"。其实上下文 ≠ 记忆。"记忆"是要跨会话、跨重启保存的；而上下文是一次推理里的临时窗口——窗口结束（或者到下一轮），窗口里的字对模型就"看不见"了，除非重新塞进下一轮的 prompt。

3. 核心机制或组成

上下文本身不是一个孤立概念，它由多个机制支撑：

组成作用常见误解
Tokenizer（分词器）把自然语言切成 token以为"字符数 = token 数"，其实中文一个字通常 1-2 个 token
Context Window（窗口）单次推理可容纳的最大 token 数以为窗口越大模型越聪明，其实是可用信息量更大
Attention（注意力）决定 token 之间相互"看见"强度以为所有 token 都被同等对待，其实位置靠后、稀疏的 token 容易被"忽略"
Instruction Hierarchy系统提示 > 用户提示 > 工具结果以为所有 prompt 是平等的，其实冲突时模型按层级取舍
Compaction / Editing当上下文将满时主动压缩/清理以为上下文满了必须"再开一轮"，其实可以原地压缩[4]

用一张图把它和 Agent 的工作流挂上钩：

  C -->|llm.generate| O[Response]
  O --> C
  C -- 接近上限 --> Comp{上下文管理}
  Comp -- 压缩/摘要 --> C
  Comp -- 写入外部 memory --> Mem[(外部存储)]
  Mem -- 引用/检索 --> RAG

其中"上下文管理"是近年被独立提出来的工程方向[1]，专门解决"模型有窗口，但任务不结束"的矛盾。常见策略包括：

  • Just-in-time 检索：不预先塞满上下文，让 Agent 在需要时主动查[1]。
  • Compaction：到上限附近自动摘要/剪枝，腾出空间[4]。
  • Memory Tool：把重要信息写到外部文件，需要时再读[4]。
  • 分层指令（Instruction Hierarchy）：区分系统提示 vs 工具结果，避免用户/工具内容覆盖关键约束。

4. 一个具体应用场景

用户指令："把项目仓库过去 30 天的所有 PR 总结成一份周报，列出风险 PR。"

输入：30 天 PR 列表（粗筛 200 条，平均每条含 1k 字 = 200k 字 = 约 ~300k token）。

处理：

  1. 不要直接把 300k token 塞进上下文——大多数窗口塞不下，超出的会直接被截断。
  2. 第一阶段：用一个便宜的 LLM 调用，just-in-time 检索：遍历 PR，把每条 PR 摘要 + 风险标签写到本地索引（这本身就是一种"上下文工程"的输出）。
  3. 第二阶段：把"风险 PR 候选 + 简短说明"（约 5k-10k token）放进 LLM，让它总结周报。
  4. 第三阶段：模型回答后，把总结再写进 Memory，下次可以直接复用。

输出：一份精炼的周报（约 1k 字），原始数据保存在外部存储而不是上下文里。

这个例子的关键不是"窗口越大越好"，而是主动调度上下文：让窗口始终装得下"真正要被模型当下思考的事"，把"原材料"留在外部。这是 Anthropic 自家产品（Claude Code、Manged Agents）也在用的思路[1][4]。

5. 容易混淆的问题与使用边界

易混点本概念相邻概念判定方法
上下文 vs 记忆临时、本次推理可见跨会话、跨重启持久是否在会话结束后还能用
上下文窗口 vs 有效上下文理论上能装下模型真能稳定利用看任务是否复杂 + 中段是否"丢信息"
长上下文 vs RAG把一切都装进窗口按需检索再喂给模型看是否检索+按需加载[1]
Token vs 字符数模型计量单位人类字数看分词器；中文 token ≠ 字符数

使用边界

上下文友好场景：单次对话、文档问答、一次性分析；同时希望"全在视野里"。

必须做上下文管理的场景：Agent 多步任务、长代码库分析、跨数据集分析、对话轮数 > 几十轮——否则容易"上下文腐烂 / 上下文污染"。

常见上下文污染表现（个人判断 + 部分来自 Anthropic 博客[1]）：

  • 模型开始引用自己没见过的工具结果。
  • 被工具返回的错误信息带偏，越纠越错。
  • 中段的细节被后来的内容覆盖（俗称"Lost in the middle"现象[3]）。
  • 用户的原始目标被工具噪声淹没，最后跑偏。

6. 自测问题

  1. Q："100k 上下文窗口"是不是等于"能稳定利用 100k 的事实"？
    要点：不是。窗口是物理上限，模型在不同位置的注意力分布并不均匀——靠近开头和结尾的内容最稳，中段最容易"看不清"（Lost in the middle）。
  2. Q：举出三种"上下文工程"的常见手段。
    要点：Just-in-time 检索（按需加载）/ Compaction（到顶时摘要压缩）/ Memory Tool（写到外部按需引用）/ Instruction Hierarchy（系统提示优先于工具结果）[1][4]。
  3. Q：RAG 和"长上下文"是互斥吗？什么时候选哪个？
    要点：不互斥。RAG 适合"原材料巨大 + 每次只需要一段"；长上下文适合"任务需要模型同时看见多个事实"。两者可叠加使用[1]。
  4. Q：Agent 跑久了为什么会"迷失"，如何识别？
    要点：主因是上下文被工具结果/错误信息占据，原本的原始目标被稀释；可观察的现象包括：开始引用未见的输出、重复之前的失败、丢失最早的目标陈述。缓解办法是主动 compaction + 外部 memory 引用[4]。

8. 与其他概念的关联

  • 与"Agent"：Agent 的整个对话历史 + 工具结果都堆进 LLM 上下文，上下文是 Agent 当下的"视野"。上下文管理差，Agent 一定差；上下文管得好，Agent 能跑得很长[1][2]。
  • 与"Skill"：Skill 的内容会进入上下文。Skill 写得很冗长 = 直接占用窗口；写得很精炼 = 留下更多预算给真正的工作。
