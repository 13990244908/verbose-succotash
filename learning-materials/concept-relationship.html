Agent / 上下文 / Skill — 三者关系

一句话定位：Agent 是执行者，Context 是它的视野，Skill 是它的操作手册。三者共同决定一个 LLM 应用能跑多远。

1. 学习目标 & 关键问题

读完能做：

  1. 用一句话讲清"Agent / 上下文 / Skill"三者的角色与关系。
  2. 画出三者在一次任务里的相互作用图。
  3. 解释"上下文窗口大小"如何直接约束 Agent 的能力上限。
  4. 解释"Skill"如何沉淀可复用的任务知识，并对 Agent 提供长期价值。
  5. 判断一个工程问题"应当在哪个层面解决"（改 Skill / 改上下文管理 / 改 Agent 流程）。

会回答：

  • Agent 跑久了为什么"越来越笨"？是它忘了，还是上下文满了？
  • 为什么 Skill 设计得冗长反而降低 Agent 表现？
  • Skill 与 Tool、与 Subagent 的边界在哪？
  • 不写 Skill，可不可以？我能不能只靠大 prompt 完成同一件事？

三条核心断言：

  1. Agent 是循环的发动机。没有 Agent，LLM 只是被动答题器；有了 Agent，LLM 才有了"看着办做下去"的能力[1]。
  2. Context 是 Agent 当下的视野。视野越清晰、越相关，Agent 越能稳定工作；视野被噪声占据，Agent 一定会迷失[2]。
  3. Skill 是把"经验"沉淀下来的结构化模块。Skill 不是循环，而是被循环消费的资料——专门替 Agent 省下每次都要重新讲一遍的成本[3]。

3. 上下文如何影响 Agent 的工作

这是写作时最容易被忽视的因果链。把它拆开来：

上下文现象对 Agent 的影响工程对策
上下文窗口小Agent 多步动作没法装回视窗，容易丢失中间结论外置记忆（Memory Tool）/ 把中间结果落盘后再引用[4]
上下文被噪声占满Agent "记住"的多是工具错误与重复内容，原始目标被稀释Compaction / 主动摘要 / 按需检索（just-in-time）[2][4]
上下文里同时塞太多 SkillSkill 之间互相稀释，Agent 反而不知道该用哪个Skill 按 description 严格分工 / 一个 Agent 只挂必要的 Skill
用户指令 < 上下文权重工具结果反向覆盖 system prompt用 Instruction Hierarchy 把系统提示提到更高优先级
上文引用了错误信息Agent 在错误前提上继续推理，越走越偏发现错误立即用 patch 工具改写上下文（context editing）

一个具体例子：

任务：让 Agent 改一个 200 个文件的代码库。

没有上下文管理的做法：把 200 个文件全文都塞进上下文，溢出、丢失关键文件、Agent 改一个忘了另一个。

有上下文管理的做法（Anthropic 推荐[2][4]）：Agent不预先加载全部文件，而是按文件名清单逐步打开；处理完一个文件把"修改要点"写回上下文，原文件留在磁盘。上下文始终保持"我正在改哪些文件 + 当前文件的关键信息"。

一句话总结：上下文管得好的 Agent，能把"短期记忆"和"长期材料"分清。

4. Skill 如何沉淀可复用的任务知识

Skill 与 Prompt / 裸 description 的本质差别，是它能 沉淀。沉淀意味着：

  • 能版本管理（Git），可以演进。
  • 能跨项目共享（项目级 Skill 跟仓库走；用户级 Skill 跟个人走）。
  • 能附资源（脚本、模板、字典），用代码替代不稳定的 token 生成。
  • 能复用别人的工作（市场 / Marketplace 装一个就行）。

沉淀的经验具体长什么样？

  • 领域知识：企业术语表、合规清单。
  • 流程步骤：标准作业流程（SOP）、失败重试规则。
  • 工具与脚本：数据格式转换、表格清洗。
  • 模板：合同模板、周报模板、PPT 主题。
  • 检查清单：发布前自检、代码 review 标准。

具体案例：本作业里的 concept-explainer Skill。把它当成一个"把任意概念学习任务沉淀成 Skill"的范例：

层沉淀的是什么对应文件

如果不用 Skill，每次要写"概念学习资料" 都得把这套流程重新讲一遍，而且讲的内容每次都可能漂移。写成 Skill 后：

  • 同一流程被复用 3 次（Agent / 上下文 / Skill 三份资料就是这个 Skill 的首批"消费者"）。
  • 以后想学新概念（Transformer / REST / 决策树），一句话调 Skill 即可。
  • 发现流程有疏漏（如下次加"概念对比"小节），直接改一份 SKILL.md，下次起所有资料都跟着改。

6. 三者配合的工作流（多步例子）

用一个完整例子把三者放到一起：让 WorkBuddy Agent 帮一个老师批改 50 份学生作业（Word）。

sequenceDiagram
  participant U as 老师
  participant A as Agent
  participant S as Skill
(grader-skill)
  participant C as 上下文窗口
  participant L as LLM
  U->>A: 提交 50 份作业
  A->>S: 加载 grader-skill 元数据
  S-->>A: 触发规则: "批改作业"
  A->>S: 加载 SKILL.md 正文
  S-->>A: 评分标准 + 流程 + 模板
  A->>C: 注入 system prompt (含 Skill 摘要)
  loop 每份作业
    A->>A: 读取作业文件 (工具)
    A->>C: 把作业正文 + 评分要点加入上下文
    A->>L: 调用 LLM 评分
    L-->>C: 返回分数 + 评语
    A->>C: 摘要写入 (避免上下文腐烂)
  end
  A->>U: 输出汇总 Excel

注意哪三件事在同时发生：

  • Agent（中间那列 "A"）作为"循环发动机"驱动整个流程。
  • 上下文（"C"）始终是 Agent 与 LLM 之间的"窗口"——批改第 30 份作业时，第 1 份的内容已经被摘要压走。
  • Skill（"S"）提供"评分标准 + 模板 + 流程"——如果换科目或换年级，调一个 Skill 即可，Agent 和上下文策略不用动。

7. 工程判断：问题应当在哪个层面解决？

你观察到的现象最可能的根因先在哪一层修
Agent 跑来跑去都在干重复的事没有沉淀抽出 Skill
Agent 后期越来越固执或开始胡说上下文被噪声占满加 compaction / 主动摘要
Agent 不知道什么时候该用哪个工具工具集过大、决策信号乱收紧工具集或拆 Subagent
Agent 输出格式每次都漂没有模板把模板放进 Skill 的 assets/
调了一次 Skill 后下次就不调了description 没写触发条件改 SKILL.md 的 description
Agent 跑得快但不可靠逻辑本应确定性化却留在 prompt用 scripts/ 替换相关 prompt

8. 自测问题

  1. Q：Agent 跑久了越来越笨，往往不是"模型退步"，而是？
    要点：上下文被噪声占满、原始目标陈述在工具结果的中段被稀释[2][4]。
  2. Q：Skill 写得太长反而降低 Agent 表现，为什么？
    要点：Skill 内容加载进上下文占据窗口；过长则挤占"真正的工作"剩余预算，还会稀释 Agent 的判断。把详细内容拆 references / 用 scripts 替代确定性逻辑[3][4]。
  3. Q：不写 Skill，可不可以只靠一条很长的 system prompt 撑住？
    要点：可以短期撑，但不能沉淀、不能升级、不能团队共享、不能加脚本与模板。任务一旦要复用，"prompt 写法"会变成单点故障——这就是为什么 Agent 生态都在推 Skill 化[3]。
  4. Q："窗口大小"和"能不能稳定利用"是一回事吗？
    要点：不是。窗口是物理上限，"稳定利用"是模型在不同位置注意力的差别；靠近开头与结尾的内容最稳，中段最容易丢失（Lost in the middle[5]）。窗口不是越大越好，长上下文要配合"按需检索"。
