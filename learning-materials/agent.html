Agent

一句话定位：能"看现在怎样 → 想下一步 → 调用工具 / 改环境 → 再看"的执行体，它让 LLM 从答题机器升级成能完成任务的执行者。

2. 个人解释

我自己的理解里，Agent 这个词被到处贴标签，但其实一句话就能讲清楚：

  • LLM 是会读会写的引擎：你问一句，它答一句。
  • Agent 是会自己看着办完成任务的执行者：它有"手"（工具）、"记忆"（上下文）、"做事的循环"（观察-思考-行动-再观察）。

判别一句话是否在聊 Agent，关键是看有没有闭环。只要它能"动手"（调用工具、写文件、查库、发请求）并根据结果决定下一步，那就是在聊 Agent；否则只是普通 LLM 问答。

很多产品叫自己"Agent"但其实只是把 Tool Use 接上去、prompt 里写几个步骤、跑一次就结束。这种"假 Agent"和真 Agent 的差别就在于：闭环有没有真正跑起来。参考 Anthropic 自己怎么定义 Agents："LLMs autonomously using tools in a loop"[2]——自主和循环两条同时满足才是。

3. 核心机制或组成

一个能稳定运行的 Agent，大致由五个部件拼起来：

部件作用常见实现
决策中枢把当前状态变成"下一步该干什么"LLM（带 system prompt + 工具描述）
工具集Agent 能做的事 = 手和脚Function Calling / Tool Use / MCP 工具
记忆系统短期 + 长期，覆盖单步和多步短期=消息历史；长期=外部存储 + 检索
规划把目标拆成步骤或子目标Plan-and-Execute / ReAct / Tree of Thoughts
循环机制让"观察-行动-再观察"真的能转起来Agent 框架（LangChain、Claude Agent SDK、WorkBuddy Agent）

用一张图把它串起来（ReAct 风格[1]）：

flowchart LR
  U[用户目标] --> O[观察
当前状态]
  O --> T[思考
下一步动作]
  T --> A[行动
调工具 / 改环境]
  A --> O
  A --> Done{目标完成?}
  Done -- 否 --> T
  Done -- 是 --> R[返回结果]

ReAct 的关键在于：思考和行动在同一个回合里交替出现。LLM 不是"想好了再动"，而是"一边做一边想，做错了就改方向"。这种"边做边纠"的特性正是 Agent 比起单轮 LLM 强大的地方[1]。

4. 一个具体应用场景

用户指令："帮我查一下明天北京的天气；如果会下雨，订一把伞送到公司前台。"

处理链路：

  1. 观察（Observation）：当前状态=用户刚发来指令，工具记录=天气 API、订单 API、地址簿。
  2. 思考（Thought）：决策中枢思考"我得先拿天气，才能决定是否下单；参数是地点=北京、日期=明天"。
  3. 行动（Action）：调用 get_weather(city="北京", date="明天")。
  4. 观察：发现 rain_probability=85%，高于触发线 60%。
  5. 思考：决策中枢下一步应当"下单伞，送到公司前台"，查找公司地址。
  6. 行动：调用 lookup_address(name="公司前台") → 拿到地址。再调用 order(item="折叠伞", ship_to=address)。
  7. 观察：下单成功，订单号 20260905-001。
  8. 结束：以自然语言告知用户："明天有雨，已下单一把折叠伞到公司前台，预计明早 9:00 前送达。"

输出：一句自然语言通知 + 订单凭证链接。

注意其中第 4 步触发了第二个动作——这正是"循环"的体现。如果只是一个"if-else + 两次 API"的脚本，Agent 的价值会消失；用户改口"如果下雨顺路买杯咖啡"时，重写代码又会成为新工作量。Agent 的好处在于它能自然地扩展动作列表，而不需要改程序流程。

5. 容易混淆的问题与使用边界

易混点本概念相邻概念判定方法
Agent vs LLM 问答多步循环、调用工具单轮生成文本看是否调用了外部工具 / 是否多次往返
Agent vs WorkflowLLM 自主决定路径代码写死的步骤链看下一步该做什么是谁决定的[2]
Agent vs Copilot / 副驾主动执行任务建议型，每步由人确认看是否"无人值守"完成全部步骤
Agent vs 多智能体（Multi-Agent）一个 LLM 决策中枢多个 Agent 协同看有没有多个独立决策主体

使用边界

适合用 Agent 的任务：多步、依赖外部信息（搜索/数据库/内部系统）、路径不可预测、需要从错误中恢复、结果难以一次性答出（例如研究、写代码、运维调查）。

不适合用 Agent 的任务：翻译、摘要、模板化生成、确定性的数据格式转换——直接调 LLM 就行，加循环只是浪费 token 和稳定性。

慎重使用 Agent 的任务：对外发送消息、金融交易、不可逆操作——必须考虑人审 + 重试机制。Anthropic 也建议对"难以撤销"的动作保留确认环节[2]。

6. 自测问题

  1. Q：用 1 句话定义 Agent，并指出它和普通 LLM 调用的关键差别。
    要点：Agent 能自主循环调用工具完成多步任务；普通 LLM 调用只是一问一答，不调用、不循环。
  2. Q：ReAct 中的 R 和 A 各代表什么？它解决的是什么问题？
    要点：R = Reasoning（推理）、A = Acting（行动）。它把"思考"和"行动"交织进行，解决的是纯 CoT 推理容易幻觉、纯行为决策不会纠错的两个极端问题[1]。
  3. Q："ChatGPT + 一堆工具"是 Agent 吗？什么时候不是、什么时候是？
    要点：仅有工具不够。要成为 Agent 必须形成"使用工具 + 看结果 + 再决定下一步"的闭环。
  4. Q：Anthropic 为什么把"workflow"和"agent"严格区分？实践中怎么选？
    要点：Workflow 路径写死、可预测、易调试；Agent 灵活但成本高、不稳定。能用 workflow 解决就别上 Agent；只有当任务路径不可枚举或需要恢复时才选 Agent[2]。

7. 参考来源

  1. ReAct: Synergizing Reasoning and Acting in Language Models — Yao et al., 2022 (ICLR 2023)。ReAct 范式的原始论文，2022 年 10 月提交，2023 年 ICLR 终版；提出"Thought / Action / Observation"交替循环的范式，并附项目页 react-lm.github.io。
  2. Anthropic Engineering: Building effective agents — Erik S. & Barry Zhang, 2024-12-19。Anthropic 给出的工作流 vs Agent 区分、五种基础模式（prompt chaining / routing / parallelization / orchestrator-workers / evaluator-optimizer）、ACI 设计原则；本文页面顶部提示自 2024-12 以来工具生态有变化，最新做法参见 Claude Managed Agents。
  3. Anthropic Tool Use GA。Anthropic 工具调用能力 GA 公告，是"Function Calling / Tool Use"产品化基础，本 Agent 资料中"手和脚"的来源。
  4. WorkBuddy 简介。本作业使用的 Agent 环境官方概述；WorkBuddy 的"自主规划执行"和"自动操作本地文件"是 Agent 思路在办公场景的典型落地。

8. 与其他概念的关联

  • 与"上下文"：Agent 的整个对话历史 + 工具结果都堆进 LLM 上下文；上下文窗口越大，Agent 才越能"看清全局"。上下文管理能力直接决定 Agent 能跑多长的任务。
  • 与"Skill"：Skill 把"完成某类任务的领域知识 + 步骤"沉淀下来。Agent 配上 Skill，就相当于一个新人配上一本操作手册——不用每次都从零问 LLM。
