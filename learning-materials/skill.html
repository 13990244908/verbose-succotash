Skill（技能 / 技能包）

一句话定位：Skill 是把"完成某类任务的领域知识、步骤、脚本、模板"打包成结构化文件夹，让 Agent 在合适场景下像调用一份"操作手册"一样按需加载。

1. 学习目标 & 关键问题

读完能做：

  1. 用一句话讲清 Skill 是什么、与裸 prompt 的本质差别。
  2. 说出一个 Skill 包的三个标准组成（SKILL.md / references / scripts 或 assets）。
  3. 列出至少 3 种"应当抽成 Skill 而不是裸 prompt"的场景。
  4. 区分项目级 Skill、用户级 Skill 与系统级 Skill 的存放位置与适用场景。
  5. 在你的工作目录里创建、调用、调试一个最小的 Skill。

会回答：

  • Skill 和 prompt 到底有什么不一样？是不是只是"换个名字的 prompt"？
  • 为什么需要 SKILL.md 这种结构化的 markdown，而不是直接在系统提示里写长 prompt？
  • "按需加载"在工程上是怎么实现的？Agent 怎么决定该用哪个 Skill？
  • Skill 和 Tool / Subagent / Plugin 这些相邻概念怎么区分？

2. 个人解释

我自己理解的 Skill 用一句话讲：

Skill = 一份标准化的"岗位操作包"。它不是单个 prompt，而是 SKILL.md（怎么干）+ references（更多细节）+ scripts / assets（重复劳动用工具）三件套。

用一个更接地气的比喻：

  • LLM 像是一个多面手新人，它什么都能聊两句，但每个岗位都得现学。
  • Skill 像公司给新人准备的"岗位入职包"：标准操作流程 + 表单模板 + 系统入口 + 历史踩坑记录。
  • 没有 Skill 时，新人每次都得重新问"咱们公司报表怎么出"；有 Skill 时，答案是"打开 report-generator 这个 Skill，照着做"。

很多新手以为"Skill 不就是一段 system prompt？" 不是的。差别在于三个地方：

  1. 结构化：Skill 有约定俗成的目录结构与 YAML frontmatter，机器能解析、人也能读。
  2. 可复用：Skill 是独立的文件夹，可以版本管理（Git）、被分享（pull request）、跨项目共享。
  3. 可附加资源：Skill 能带可执行脚本（python / bash）和静态资产（模板、图标、样例输出），覆盖那些靠 token 生成不靠谱的确定性任务。

3. 核心机制或组成

一个规范的 Skill 通常由以下部件拼成：

部件作用何时用
SKILL.mdSkill 的"自述"：YAML frontmatter + 工作流说明必备
references/按需加载到上下文的详细文档文档较长、希望按子话题拆开时
scripts/对确定性任务直接写脚本逻辑固定、token 生成不可靠时（旋转 PDF、跑测试）
assets/模板、字体、图标、样例文件需要被复制进最终交付物中时

更关键的机制是"加载策略"的三级渐进：[2]

flowchart LR
  M["元数据
name + description
~100 字"] --> R[决策触发
是否相关]
  R -- 相关 --> B[加载 SKILL.md 正文
不超过 5000 字]
  B -- 需要细节 --> S[加载 references/
按需查阅]
  B -- 需要跑代码 --> C[执行 scripts/
无需载入上下文]

这个三级加载的设计是 Skill 能"不撑爆上下文"的关键：不是每个 Skill 的所有内容都进上下文，而是在 Agent 真的需要时才引用。

SKILL.md 的最小骨架

---
name: <skill-name>
description: |
  This skill should be used when ...
  不能只写一行；至少说明触发场景和产出
agent_created: true   # 若是 AI 自己创建的，加上以便后续修改
---

# <Skill 名称>

## 适用场景
## 输入信息
## 工作流（分步骤）
## 输出结构
## 自检要求
## （可选）范例

4. 一个具体应用场景

任务：每周一批 10 份学生报名表（Excel），需要按统一模板汇总输出成一份 Word 报名册。

用裸 prompt 的做法：

  1. 写一段长 prompt："你是助理，请读 Excel……"
  2. 每次都得复制粘贴这份 prompt。
  3. 用户改要求（比如新增一列）—— prompt 要全部重写。
  4. 同事也想用 — 不知道这份 prompt 在哪。

用 Skill 的做法：

  1. 在 .workbuddy/skills/student-roster/ 下创建一个 Skill，包含：
    • SKILL.md：说明输入是 Excel 列表、输出是固定模板 Word、中间要做的核对步骤。
    • references/roster-template.md：Word 排版要求（字号、表头、命名规范）。
    • scripts/excel_to_word.py：一个确定性的转换脚本（不依赖 LLM）。
    • assets/template.docx：空白模板。
  2. 以后每周只需对 WorkBuddy 说："用 student-roster 处理这周的 Excel。"
  3. 改要求？改 SKILL.md 一处即可。共享给同事？把这个文件夹发过去。

为什么这样更稳：确定性部分（文件格式转换、姓名校验）交给 scripts/，只有"理解 + 决策"才走 LLM。这样既能复用，又把 token 成本和幻觉风险压到最小。[1]

5. 容易混淆的问题与使用边界

易混点本概念相邻概念判定方法
Skill vs Prompt结构化、可版本化、可附资源纯文本、写一次用一次看有没有目录 + 元数据
Skill vs Tool"知道怎么干"指导LLM"直接能干"调用外部动作Skill 不直接产生副作用；Tool 才会
Skill vs Subagent主 Agent 加载的辅助内容独立的子决策体看是不是新开一个决策循环
Skill vs PluginAI 用的、可被 AI 加载外部应用扩展、给人看的 UI看消费者是 LLM 还是人
项目级 vs 用户级 Skill随仓库走，团队可共享跨项目跟随个人看路径：.workbuddy/skills/ vs ~/.workbuddy/skills/[2]

使用边界

应当抽成 Skill 的场景：

  • 同一类任务要被多次复用（如本作业的"概念学习资料生成"）。
  • 任务需要对 LLM 之外的工具/脚本 配合。
  • 任务需要按团队/项目沉淀领域知识（如品牌规范、合规要求）。
  • 任务涉及不可逆操作，需要约定好的检查清单。

不必抽成 Skill 的场景：

  • 只用一次的一次性提示。
  • 用户当前提问里已经把全部要求说清了的临时任务。
  • 暂未稳定（频繁改要求）的工作流——先稳定再抽 Skill。

Skill 的反模式（个人判断）：

  • 把所有信息全塞在 SKILL.md 里（应当拆 references/）。
  • 把"应当确定性执行"的逻辑写在 prompt 里（应当 scripts/）。
  • description 写得太笼统，导致 WorkBuddy 不能自动识别该加载。
  • 多 Skill 重名 / 描述重叠，导致选择错乱。

6. 自测问题

  1. Q：SKILL.md 顶部必须包含哪些字段？
    要点：name（必需）与 description（必需），推荐 agent_created: true（用于 AI 自己创建的 Skill 后期管理）。description 必须写明"什么时候该用"，让 WorkBuddy 能自动触发[1][2]。
  2. Q：Skill 和 Tool 的根本区别是什么？
    要点：Tool 让 LLM 能"动手"（调用 API、改文件、发请求）；Skill 让 LLM 能"照着做"（按约定步骤、查内部资料）。Skill 不直接产生副作用，Tool 才会。
  3. Q：什么样的任务应该用 scripts/ 而不是写在 prompt 里？
    要点：逻辑固定、能用代码表达、对一致性要求高的部分（如格式转换、数值计算、文件 IO）。LLM 生成易出错的环节用脚本确定性完成；只有"理解上下文"的部分留给 LLM[1]。
  4. Q：项目级 Skill 放在哪个目录？用户级 Skill 放在哪？
    要点：项目级：仓库内 .workbuddy/skills/<name>/SKILL.md，跟仓库走、团队可见；用户级：~/.workbuddy/skills/<name>/SKILL.md，跨项目跟个人。个人 Skill 需要先在 WorkBuddy 中加载/启用[2]。

  1. Claude Blog: Introducing Agent Skills — 2025-10-16。Anthropic 在 Claude 平台正式公布 Agent Skills，强调 Skills 是含指令/脚本/资源的文件夹，Claude 会"按需加载"；并给出 4 个核心特性（Composable / Portable / Efficient / Powerful）。
  2. WorkBuddy 简介。说明 WorkBuddy 是腾讯出品的全场景 AI 办公工作台，支持"自主规划执行 + 多步骤复杂任务"，对个人 Skill 的存放与加载策略与 Anthropic Claude 平台一致（项目级 .workbuddy/skills/、用户级 ~/.workbuddy/skills/）。
  3. Anthropic Engineering: Effective context engineering for AI agents。将 Skill 类比为"上下文工程中 examples / message history 之外的结构化模块"，并指出"scripts instead of tokens"是高效的关键。

8. 与其他概念的关联

  • 与"Agent"：Agent 是执行体（决策 + 工具 + 循环）；Skill 沉淀 Agent 的"经验手册"。没 Skill 的 Agent 像新员工，啥都要问；有 Skill 的 Agent 像熟练员工，能按手册批量作业。
  • 与"上下文"：Skill 的内容会进入上下文，写得冗长 = 占用窗口；写得精炼、按需加载 = 把窗口留给真正的工作。Skill 设计本身就是一种"上下文工程"实践[3]。
